# Чеклист выпуска кабинета Askwise

Этот список нужен перед первым реальным запуском. Он не содержит секретов и
не заменяет подробные инструкции в
[`pipeline-service/docs/production-operations.md`](../pipeline-service/docs/production-operations.md).

## До включения production

- [ ] Собрать фронтенд: `npm run lint` и `npm run build`.
- [ ] В сервисе выполнить: `npm run typecheck`, `npm test`, `npm run build`.
- [ ] Создать отдельные production-значения для `WEB_API_USERNAME`,
  `WEB_API_PASSWORD` и `CONTENT_API_TOKEN`; не использовать тестовые учётные
  данные и не записывать секреты в Git.
- [ ] Задать один публичный HTTPS-origin в `WEB_API_ALLOWED_ORIGINS`.
- [ ] Включить `NODE_ENV=production` и `WEB_API_SECURE_COOKIES=true`.
- [ ] Подключить доверенный почтовый шлюз для сброса пароля: задать
  `PASSWORD_RESET_BASE_URL` с публичным HTTPS-адресом кабинета и
  `PASSWORD_RESET_WEBHOOK_URL` с HTTPS endpoint шлюза. Не добавлять почтовые
  ключи или `PASSWORD_RESET_WEBHOOK_SECRET` в frontend или Git; на стороне
  шлюза проверять HMAC-подпись `X-Askwise-Signature`.
- [ ] Проверить, что `DATA_DIR` расположен вне репозитория и доступен только
  сервисному пользователю.
- [ ] Включить ежедневный backup по
  `pipeline-service/deploy/lexis-backup.timer` и проверить manifest первой
  резервной копии.

## Staging-приёмка

- [ ] На отдельном домене и с отдельным `DATA_DIR` открыть `/api/health` и
  `/api/ready` — оба должны вернуть `200`.
- [ ] Пройти регистрацию, вход и выход.
- [ ] Запросить сброс пароля для staging-пользователя, получить письмо,
  открыть ссылку, задать новый пароль и убедиться: старый пароль и прежняя
  сессия больше не работают, а повторное открытие ссылки отклоняется.
- [ ] Переименовать компанию, пригласить редактора и наблюдателя, принять
  приглашения и убедиться, что роли ограничивают действия ожидаемым образом.
- [ ] Создать одну тестовую заявку, добавить в очередь и убедиться, что
  обновления в кабинете приходят через real-time соединение.
- [ ] Провести одну контролируемую статью до публикации в тестовую CMS.
- [ ] Проверить кабинет на ширинах 360 px, 768 px, 1024 px и desktop.

## После выпуска

- [ ] Наблюдать `/api/health` и `/api/ready` не реже раза в минуту; тревога
  нужна после двух неудачных проверок подряд.
- [ ] Проверять свежесть backup раз в сутки и восстановление в staging — раз в
  квартал.
- [ ] Не выводить в логи cookie, CSRF-токены, пароли, API-ключи и полный текст
  пользовательских брифов.
- [ ] Перед любым обновлением сделать backup и повторить staging-приёмку.
